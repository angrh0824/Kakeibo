# 家計簿 Ver2.0 規模・上限・拡張判断

最終更新: 2026-08-13

## 1. 結論

家計簿が増えるたびにFirestoreデータベース、Cloud Storageバケット、Cloud Runサービスを新設する構成ではありません。1つの共通基盤内で`householdId`ごとにデータを論理分離しています。

そのため「家計簿が100個になったら停止する」という固定上限はありません。家族・友人数名から数十家計簿の現在想定では十分な余裕があります。

将来先に問題になるのはGoogle Cloudの保存可能件数ではなく、現在のアプリが一部の画面で全件を読み込むこと、画像を含むAI解析の同時実行、OpenRouterの応答時間・利用制限・実費です。

## 2. 現在のデータ分離

```text
Google Cloudプロジェクト: 1つ
├─ Firestoreデータベース: 1つ
│  └─ households/{householdId}
│     ├─ receipts/{receiptId}
│     ├─ usage_events/{eventId}
│     ├─ usage_periods/{YYYY-MM}
│     ├─ billing_state/current
│     └─ billing_adjustments/{adjustmentId}
├─ Cloud Storageバケット: 1つ
│  └─ receipts/{householdId}/YYYY/MM/{画像}.jpg
└─ Cloud Run API: 1サービス
```

新しい家計簿を作ると、共通Firestore内に家計簿文書と必要なサブコレクションが追加されます。新しいデータベースやサーバーが1台ずつ増えるわけではありません。

家計簿Aと家計簿Bのデータは同じFirestoreに保存されますが、すべてのAPIでGoogleログイン、選択中の`householdId`、メンバー権限を照合します。画像パスも`householdId`で分離します。

## 3. 何が増えるか

| 利用内容 | 増えるもの | 主な料金・負荷 |
|---|---|---|
| Googleアカウント追加 | `platform_users`文書 | Firestore読書き |
| 家計簿追加 | `households`文書 | Firestore読書き |
| レシート登録 | 家計簿配下の`receipts`文書 | Firestore保存・読書き |
| 画像解析 | 非公開JPEG、AI利用イベント | Storage容量、OpenRouter、Cloud Run |
| 月が変わる | `usage_periods/{YYYY-MM}` | 少量のFirestore保存 |
| 支払い確認・免除 | `billing_adjustments`文書 | 少量のFirestore保存 |

レシート文書には店舗、日時、合計、品目配列、画像参照を保存します。画像本体はFirestoreへ入れずCloud Storageへ保存します。

## 4. サービスごとの上限

### Firestore

本アプリ独自の家計簿総数・レシート総数の固定上限はありません。主なハード制限は1文書最大1MiBです。通常の数十品目のレシートは十分小さいため、一般的な利用でこの制限へ達する可能性は低いです。

無料枠の代表値は保存1GiB、読取50,000件/日、書込20,000件/日、削除20,000件/日です。請求先を有効化したプロジェクトでは、無料枠超過は原則として即停止ではなく従量課金になります。

公式資料:

- [Firestoreの使用量と上限](https://firebase.google.com/docs/firestore/quotas)
- [Firestoreの料金と無料枠](https://firebase.google.com/docs/firestore/pricing)

### Cloud Storage

画像は最大辺1800px、目標1.5MB以下、JPEG品質82を基準に圧縮して1つの非公開バケットへ保存します。Cloud Storageには本アプリ規模で問題になるような小さな総オブジェクト数上限はなく、保存件数より容量と読み書き料金が増えます。

上限サイズの1.5MBで単純計算した保存容量は次のとおりです。

| 画像枚数 | 最大目安 |
|---:|---:|
| 1,000枚 | 約1.5GB |
| 10,000枚 | 約15GB |
| 100,000枚 | 約150GB |

実画像は1.5MB未満になる場合が多いため、実容量はこの最大目安より小さくなります。1枚の画像から複数レシートを検出した場合も、画像本体は1つです。

公式資料: [Cloud Storageの割り当てと上限](https://cloud.google.com/storage/quotas)

### Cloud Run

2026-08-13時点の本番設定は次のとおりです。

- 1 vCPU
- 512MiBメモリ
- 1インスタンス最大同時リクエスト数80
- 最大20インスタンス
- タイムアウト300秒
- request-based billing
- startup CPU boost有効

設定値だけを掛けると最大20×80リクエストですが、これは同時AI解析1,600件の性能保証ではありません。画像の展開・圧縮でメモリを使い、外部AIの待ち時間、OpenRouter側の制限、Cloud Runの自動スケール判断があるため、実際の安定同時処理数は負荷試験で決める必要があります。

公式資料:

- [Cloud Runの割り当てと上限](https://cloud.google.com/run/quotas)
- [Cloud Runの同時実行](https://cloud.google.com/run/docs/about-concurrency)

### 画像アップロード1回の上限

アプリ上は最大10画像、1ファイル最大15MBです。ただしCloud RunのHTTP/1リクエストサイズ上限は32MiBで、圧縮はCloud Runへ到着した後に行います。

3MB画像を10枚送ると合計約30MBにmultipartの付加情報が加わるため、32MiBへ近づきます。これは全体の保存件数ではなく、1回のアップロードだけが失敗する可能性のある上限です。

また、現在のバックエンドは同じリクエスト内の画像を順番にAI解析します。長いレシートを10枚まとめると300秒タイムアウトへ近づく可能性があります。

## 5. 現在の実装で先に遅くなる箇所

### 家計簿内のレシート全件読み込み

`GET /api/receipts`は、選択中の家計簿のレシートをFirestoreから全件取得し、API側で並べ替えてブラウザへ返します。ダッシュボードは月表示でも、通信時点では全件です。

1家計簿が数千レシートになると、Firestore読取数、API応答サイズ、ブラウザメモリ、初期表示時間が増えます。Google Cloudの保存限界より先に、ここが体感速度の問題になります。

### 管理者の全家計簿料金一覧

管理者料金画面は全家計簿を列挙し、家計簿ごとに利用月を読み取って累積残高を計算します。家計簿数×利用月数に比例するため、数百家計簿では集計方法の改善が必要です。

### メンバー・商品マスタ処理

家計簿メンバー一覧は現在の全利用者を確認し、商品マスタ一括修正と画像参照確認は対象家計簿のレシートを走査します。利用者やレシートが非常に増えた場合は専用インデックス・メンバーサブコレクション・参照カウンタが必要です。

### AI解析

通常はFirestoreより、画像ごとのOpenRouter呼び出しが時間と実費の中心です。同時利用が増えると、外部AIの429、タイムアウト、月額予算、Cloud Runメモリを先に監視します。

## 6. 現実的な規模の目安

次はGoogle Cloudのハード上限ではなく、現在の実装を変更せず快適に使うための保守的な判断目安です。

| 規模 | 判断 |
|---|---|
| 家族・友人数名〜数十家計簿 | 現状のままで十分。通常監視だけでよい |
| 約100家計簿 | Firestore読取、Storage、AI費用、API応答時間の月次確認を開始 |
| 数百家計簿 | 管理者料金集計とメンバー検索の改修を推奨 |
| 1家計簿1,000〜3,000レシート | 全件読み込みの体感速度を測定し、月別取得・ページ分割を実装 |
| 約1,000家計簿または一般公開 | 負荷試験、非同期解析、レート制限、監視・障害対応を含む再設計が必要 |

1家計簿あたり1日1レシートの場合は、10家計簿で年間3,650件、100家計簿で年間36,500件、1,000家計簿で年間365,000件です。Firestoreは保存できますが、全件読み込みを続けるほど日々の読取回数が増えます。

## 7. 拡張する場合の優先順位

### 優先度A: レシート取得のページ分割

- APIへ`yearMonth`、`limit`、`cursor`を追加
- ダッシュボードは選択月だけ取得
- レシート一覧は20〜50件ずつ追加取得
- Firestoreで日付順クエリ用インデックスを利用

これが最初に行うべき改修です。データベースを家計簿ごとに分割する必要はありません。

### 優先度B: 画像送信の分割

- ブラウザでアップロード前に圧縮
- 合計サイズを表示して32MiB未満に制御
- 複数画像を1〜3枚ずつ送信
- 画像単位の再試行と進捗保存

### 優先度C: 集計の事前計算

- 累積未精算残高を毎回全月から再計算せず状態文書へ保持
- 管理者用全家計簿サマリーを月次集計文書へ保存
- 家計簿メンバーを家計簿配下へ保持し、全利用者走査を廃止

### 優先度D: 多人数向け運用

- Cloud Monitoringの遅延・5xx・メモリ・インスタンス数アラート
- Google Cloud予算アラートとOpenRouter利用上限
- アカウント・家計簿単位のレート制限
- AI解析をCloud Tasksなどで非同期化
- バックアップ復元手順、障害時連絡、利用規約・プライバシー対応

## 8. 改修を開始する観測サイン

次のいずれかが継続したら、保存基盤の分割ではなく上記の取得・集計改善を開始します。

- レシート一覧の初期表示が2〜3秒を恒常的に超える
- `GET /api/receipts`の応答が数MB以上になる
- 1家計簿のレシートが1,000件を超える
- Firestore読取が無料枠50,000件/日へ近づく
- 管理者料金画面が5秒以上かかる
- Cloud Runでメモリ不足、5xx、最大インスタンス到達が発生する
- OpenRouterで429・タイムアウトが継続する
- 10画像アップロードで32MiBエラーまたは300秒タイムアウトが発生する

無料枠超過は必ずしも障害ではなく、従量課金へ移るサインです。「遅い」「失敗する」「費用が想定を超える」を分けて監視します。

## 9. 現時点の判断

友人数名へ提供する現状では、家計簿数やレシート数を理由に直ちに構成変更する必要はありません。1つのFirestore、1つのCloud Storageバケット、1つのCloud Runサービスを共有する現在の構成が適切です。

次回規模を拡大するときは、本書を読み、最初に「月別・ページ単位のレシート取得」と「アップロード合計サイズ制御」を実装します。
