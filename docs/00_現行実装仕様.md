最終更新: 2026-08-13

この文書は、現在このリポジトリとGoogle Cloud本番環境で動作する実装を説明します。`01_全体処理パイプライン設計.md`〜`04_名寄せアルゴリズム設計.md`は将来構成を含むため、現行動作については本書を優先します。

## 2. アカウント・承認・BAN

初めてGoogleログインした利用者は、Firestoreの`platform_users`と`signup_requests`へ`pending`状態で登録されます。承認前はレシート解析・データ・画像を利用できません。

プラットフォーム管理者には次の機能があります。

- 設定メニューの件数バッジとログイン直後のアプリ内通知で新規申請を確認
- 初回利用申請を承認
- アカウントを即時BAN
- BAN解除

BANはAPIリクエストごとに確認するため、利用中のセッションにも次の操作時から反映されます。管理者自身はBANできません。

初回申請時には`KAKEIBO_SIGNUP_REQUEST`識別ログを1回だけCloud Loggingへ記録します。Google Cloud Monitoringのログベースアラート「家計簿 - 新規利用申請」がこれを検知し、通知チャンネル`asukita824@gmail.com`へ承認画面リンク付きメールを送ります。通知間隔は最短5分、インシデント自動終了は30分です。Gmail APIや外部メール送信サービスは使用しません。アプリ内の件数バッジ・ログイン通知も併用します。

## 3. 家計簿と招待

新規承認されたアカウントには、本人がオーナーの個人家計簿を1つ自動作成します。オーナーは設定画面でGoogleアカウントのメールアドレスを指定して他の人を招待できます。

- 招待先が承認済み利用者なら、その家計簿のメンバーへ即時追加
- 未利用・承認待ちなら、管理者承認時に招待先家計簿へ追加
- 複数の家計簿へ参加している利用者は、設定画面のセレクターで切替
- 招待とメンバー解除は家計簿オーナーだけが実行可能
- プラットフォーム管理者でも、メンバーでない友人の家計簿データは閲覧不可

既存の家族3アカウントは`ALLOWED_USER_EMAILS`を移行用リストとして使い、従来データを共有する`family-main`（表示名「わが家の家計簿」）へ初回ログイン時に登録します。先頭の既存管理者アカウントがオーナーです。

## 4. データ分離と既存データ移行

レシートは次のFirestore階層へ保存します。

```text
households/{householdId}/receipts/{receiptId}
```

認証済みAPIは`X-Household-ID`を受け取り、`platform_users`のメンバー情報と照合します。選択した家計簿のメンバーでなければ`403`で拒否します。レシート一覧、登録、更新、削除、画像取得、商品マスタ更新のすべてが同じ家計簿IDに限定されます。

従来のルート`receipts/{receiptId}`は、既存家族が初回同期したときに`households/family-main/receipts`へ同じIDで冪等コピーします。移行確認後もルート文書はロールバック用として残し、新しい読み書きは家計簿配下だけを使います。

新規画像は次のCloud Storageパスへ保存します。

```text
receipts/{householdId}/YYYY/MM/{hash}-{uuid}.jpg
```

既存画像の旧パスはそのまま参照でき、再アップロードは不要です。バケットは非公開で、画像は必ず家計簿メンバー認証済みAPIを経由して取得します。

## 5. レシート読み取り・保存フロー

1. 「カメラで撮影」または「写真から選ぶ」で画像を一時選択リストへ追加します。撮影と写真ライブラリを混在でき、合計最大10枚です。
2. 撮影・選択直後には解析せず、「続けて撮影」「写真を追加」「個別に外す」「すべて外す」で内容を確定します。
3. 「選択した画像をまとめて解析」を押すと、進捗演出を待たず`POST /api/receipts/analyze`へGoogle IDトークンと選択中の家計簿IDを付けて送信します。
4. 最大15MBを検証し、EXIF補正後、最大辺1800px・目標1.5MB以下・JPEG品質82を基準に圧縮します。
5. 圧縮画像をOpenRouterへ送り、1回のマルチモーダルAI呼び出しで文字認識、品目抽出、金額補正、カテゴリ分類を行います。1画像内の複数レシートもレシート単位へ分離します。
6. 税額・税率・割引・税込合計を考慮して明細合計を印字合計へ合わせます。
7. 圧縮JPEGを選択中の家計簿専用Cloud Storageパスへ保存します。
8. レビュー画面で承認したレシートだけを選択中のFirestore家計簿へ登録します。

解析進捗は「画像を送信」「AI一括解析」「結果を準備」の3表示です。独立したOCRやカテゴリ分類APIを順番に呼んでいるわけではありません。AI応答待ちは完了率を偽装しない往復アニメーションで表示し、応答受信後の最終工程は画面データを整える短い処理だけです。

誤解を招いていた未接続の「AI解析設定」カードは削除済みです。本番モデルはCloud Runの`DEFAULT_AI_MODEL`で一括管理し、利用者や家計簿ごとには変更できません。

## 7. Firestoreコレクション

- `platform_users`: Google subject、メール、状態、管理者権限、参加家計簿と役割
- `signup_requests`: 初回利用申請と承認記録
- `households`: 家計簿名、オーナー
- `household_invitations`: 招待メール、招待先家計簿、状態
- `households/{id}/receipts`: 家計簿ごとに分離したレシート
- `households/{id}/usage_events`: OpenRouterリクエストID単位の監査用AI利用量・実費
- `households/{id}/usage_periods/{YYYY-MM}`: 月次のAI・Cloud Run・Firestore・Storage利用量集計
- `households/{id}/billing_state/current`: 現在の画像容量、残高調整額、最終調整者
- `households/{id}/billing_adjustments/{id}`: 支払い確認・免除・手動残高変更の監査履歴
- `system/billing-config`: PayPay QR画像の非公開Storage参照
- `system/legacy-receipts-to-households-v1`: 既存家族データ移行完了記録

## 8. データ保持・画面表示

- 正本はFirestoreとCloud Storageです。ブラウザ`localStorage`は家計簿選択IDだけに使用し、レシート正本には使用しません。
- Google IDトークンは`sessionStorage`へ置き、有効期限切れ・ログアウト時に削除します。
- 設定画面から選択中の家計簿データをJSONで書き出せます。
- 月セレクターでダッシュボードとレシート一覧を月別に切り替え、日付は`yy/mm/dd`で表示します。
- レシート・商品マスタの編集は選択中の家計簿メンバーだけへ反映されます。
- Firestoreは削除保護あり、Cloud Storageは公開アクセス禁止・Uniform bucket-level accessです。
- スマートフォンのモーダルは`100dvh`と端末の安全余白を使い、PixelやiPhoneのシステムUIに操作ボタンが隠れないようにします。
- ログインゲートは`VisualViewport`の表示位置と寸法へ同期し、Pixelのアプリ内ブラウザや可変ツールバー環境でもカードを実表示領域の中央へ置きます。
- レシート確認画面は本文だけを縦スクロールし、「破棄する」「承認して登録」の操作欄を常にモーダル内へ残します。
- モバイルの購入品目は横長テーブルではなく、品名・単価・数量・カテゴリ・小計を品目カードとして表示します。

## 9. 月別利用料金・累積未精算残高・使いすぎ防止

`BILLING_ENABLED=True`の本番環境では、レシート解析ごとにOpenRouter応答の`usage.cost`、入力・出力・推論トークン、モデル、リクエストIDを家計簿別に記録します。同じOpenRouterリクエストIDは二重計上しません。

Google Cloud分は次を家計簿別に記録し、東京リージョンの設定単価で概算します。

- Cloud Run: レシート関連APIの処理時間とリクエスト回数
- Firestore: アプリ処理から推定できる読み取り・書き込み・削除回数
- Cloud Storage: 画像アップロード・ダウンロード回数、通信量、現在の保存容量

Google Cloudの無料枠はプロジェクト全体へ適用され、家計簿へ厳密に分割できないため、画面のCloud費用は「無料枠適用前の保守的な概算」と表示します。OpenRouter分はAPI応答に含まれる実費です。円換算レートは`BILLING_USD_JPY_RATE`で管理します。

利用料金は`usage_periods/{YYYY-MM}`へ月別に残し、月が変わっても削除しません。各月の任意精算目安を合計し、管理者による調整を加えた金額を「累積未精算残高」として翌月へ繰り越します。

任意精算の目安は次の式です。

```text
運営協力分 = round(概算原価 × BILLING_MARKUP_PERCENT / 100, 2)
任意精算目安 = ceil(概算原価 + 運営協力分)
```

現在の`BILLING_MARKUP_PERCENT`は100です。合計のみ1円単位へ切り上げます。決済APIとの接続は行わず、管理者が非公開Cloud Storageへ登録した個人用または加盟店用PayPay QRを家計簿オーナーだけに表示します。これは友人間の任意精算用であり、支払いの強制、督促、入金確認は行いません。

個人用マイコードを登録する場合は、招待済みの友人同士で合意した立替実費などの任意精算として管理者の責任で運用します。PayPay公式は、個人送金を商品・サービスの対価受領へ使うことや、不特定多数へマイコードを掲示することを禁止しています（[加盟店向け案内](https://paypay.ne.jp/help-merchant/b0861/)、[禁止事項](https://paypay.ne.jp/help/c0442/)）。運営協力分を実際に受け取る場合は、この条件に該当しないか管理者が確認してください。

プラットフォーム管理者は、各家計簿について次を操作できます。

- 累積利用上限を0円（上限なし）から1,000,000円まで設定
- 未精算残高を任意額へ変更
- 支払い確認または免除として未精算残高を0円へ変更

残高を0円にしても月別利用履歴は変更しません。調整時点までの累積料金を相殺する調整額を保存するため、その後の新しい利用料金は再び未精算残高へ加算されます。変更前後の残高、変更者、メモは`billing_adjustments`へ監査記録します。

累積未精算残高と次回解析用予約額が累積利用上限へ達すると`POST /api/receipts/analyze`を`429`で停止します。既存レシートの閲覧・編集・バックアップは停止しません。初期上限は1,000円です。旧`billing_monthly_limit_jpy`が残っている家計簿は、初回参照時に累積利用上限として互換利用します。

計測導入前の過去利用量は遡及計上しません。

## 11. 解析速度の診断記録

2026-08-13のPixel実機確認に対応するCloud Loggingの`POST /api/receipts/analyze`は、Cloud Run受信から応答まで4.695秒でした。旧フロントエンドは実際の送信前に進捗演出だけで約2秒待ち、その後の全実処理を「カテゴリ分類中」と表示していたため、最後の工程だけが長いように見えていました。

現在は次のように改善しています。

- APIリクエストを「選択した画像をまとめて解析」押下直後に開始し、送信前の約2秒待機を撤廃
- 外部AI応答待ちを「AI一括解析」として正しく表示
- AI応答後の「結果を準備」は約0.22秒の画面準備だけに限定

Cloud Run側は画像の前処理・認証・保存よりOpenRouterのAI応答待ちが支配的です。2 vCPUへ増やすとCPU割当分の単価は概ね2倍になりますが、外部AIの待ち時間はほぼ短縮されないため、今回CPUは増強していません。家族・友人数名規模では無料枠内に収まる可能性が高いものの、性能効果がない増強は行わない方針です。料金の考え方は[Cloud Run公式料金](https://cloud.google.com/run/pricing)を参照してください。
